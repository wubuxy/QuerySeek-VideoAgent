# 实施规划：主动视频证据定位与交互工作台

日期：2026-11-19。根据本轮讨论形成的候选实施规划；不代表新增算法或页面已经实现。

## 1. 目标与当前起点

用户上传或选择已保存视频，输入事件描述与观察预算，得到浮点秒半开区间 `[start_sec, end_sec)`、实际证据帧、搜索轨迹、实耗及可下载片段。允许继续要求检查相邻区域、缩小边界或重新定位；第一版不扩展通用视频问答。

当前工作区已有 FFmpeg/ffprobe、PySceneDetect、BM25、OpenCLIP、时间与缓存契约、固定检索、adaptive/LangGraph 原型、CLI、Streamlit 演示和 pytest。现有页面已支持上传、索引、定位、证据和剪辑，但仍是演示流程，不是完整视频库与历史任务工作台。

旧二叉策略与 Qwen3-VL-8B 动作 SFT 保留为历史对照；学习“换区域 / 局部细看 / 结束”的新控制器尚未实现。既有确认集不重跑选模；历史约 2.5 分钟结果不作为自然长视频成绩。所有新算法收益均为 TODO / 未测。

本规划补充前端使用闭环，不改变 P0→P4 的研究验收顺序。当前任务授权发布规划；后续源码发布须逐文件审阅，不能把当前工作区全部改动直接提交。

## 2. 架构与实现原则

- 第一版扩展现有 Streamlit，不先重写 React/FastAPI，也不引入独立网站托管依赖。复用 `queryseek` 的检索、索引和导出入口，页面不维护另一套算法。
- 页面 / CLI → 应用服务（视频、任务、结果）→ ingest / retrieval / agent → FFmpeg、OpenCLIP、固定 VLM；研究运行器复用相同观察与成本接口。
- 新上传媒体和任务产物限制在 `outputs/` 下；配置、注册表与派生索引沿用明确的配置根目录。以服务生成 ID 和 SHA256 管理视频，不使用用户文件名作为唯一存储键。
- 元数据、任务配置、结果与运行状态持久化，页面刷新后可恢复。原视频、派生缓存和用户导出分开记录；不覆盖旧冻结结果，不隐式依赖外部归档。
- 所有区间满足 `0 <= start_sec < end_sec <= duration`；FFmpeg 仅接收已验证结构化参数，外部命令 `shell=False` 并设超时。
- Mock 始终可用且醒目标识；真实模式展示实际模型和版本，无可用真实后端时明确说明，不把 Mock 包装为真实推理。
- 密钥仅经环境变量读取；trace 不含密钥、图片原文；依赖变更更新 THIRD_PARTY.md。

## 3. P0：先交付可持续使用的最小工作台

### 3.1 用户流程与页面

| 页面 | 第一版功能 | 验收 |
|---|---|---|
| 视频库 | 上传视频与可选 SRT、保存、去重提示、标题、时长、缩略图、处理状态、原视频预览 | 同名不同内容不互相覆盖；刷新/重启后可再次选择；异常文件不进入可查询状态 |
| 定位工作台 | 选择视频、自然语言事件描述、预算设置、发起定位、继续定位追问 | 追问保留父任务引用，但拥有独立任务 ID、配置快照和明确预算 |
| 定位结果 | 播放原视频、跳至证据时间、查看候选区间与证据图片、导出/下载 MP4 和结果 JSON | 播放与导出对应源时间；导出状态和定位状态分别记录，导出失败不伪装为成功 |
| 历史任务 | 按视频查看查询、模型、参数、状态、成本和产物，重新打开或按新任务重跑 | 不依赖 Streamlit 临时 session_state 保存唯一结果；配置变化不误用旧运行 |
| 证据与过程 | 已观察位置、补看动作、来源标签、假设状态、剩余预算；块视图按后端能力展示 | 只展示真实产生的信息；未接入的块结构和学习控制器标为未实现 |

初始交互示例：上传并保存 → 等待索引 → 输入“寻找把杯子放进柜子的片段” → 选择预算 → 定位 → 查看证据 → 追问“检查起点前后” → 保存结果或下载片段。

### 3.2 后端支撑

- 抽出视频库、任务记录、结果读取和导出服务，避免业务逻辑全部写在页面回调。
- 初版面向本机单用户，任务顺序执行，状态至少包含 queued/running/completed/failed/interrupted；持久化状态并防止页面重复提交同一操作。
- 取消先采用步骤间协作终止；在途模型请求不承诺立即中止，已发生的调用与成本继续记账。进程重启后识别中断任务，按真实 checkpoint 能力决定恢复或新任务重跑。
- 上传先执行大小限制和 ffprobe 校验；视频与字幕在服务生成的路径中保存，建立字幕版本与索引配置关系。
- 用户移除视频时明确列出受影响的原文件、索引和结果，不默认级联删除历史证据；所有文件操作检查解析后路径。

### 3.3 P0 验证

使用合成 fixture 和 Mock，补充 pytest 与 Streamlit AppTest：上传/保存/去重、同名隔离、非法输入、任务持久化、刷新恢复、失败记录、历史查询、区间与导出、预算终止、路径越界和缓存配置隔离。人工走通页面完整流程。文件下载和播放器定位通过真实浏览器复核。此阶段不声称算法准确率提升。

## 4. P1：先测感知能力和合理预算

1. 冻结同一 VLM、精度、图像分辨率、输入格式、数据划分与失败计分规则。
2. 在训练/开发来源检查正确局部片段与相似干扰；区分对象匹配、动作过程、文字辨认和边界问题。
3. 建立强固定参照：全局均匀观察、相关性加覆盖选帧、固定检索后局部观察。字幕参照单独报告。
4. 先对 8/16/32/64 个总独立帧预算作小批量资源探针；OOM 或截断是实测结果，不能静默降低分辨率后混算。
5. 再比较每轮帧数与轮数的分配，避免只验证“每轮 4 张、最多 4 轮”。固定和动态流程既报告同预算上限，也报告实际成本。
6. 输出上限依据接口和截断实测选择：短动作、结构化观察、假设输出分开验证。模型的 64 个输出 token 不等于全部输入或整次任务 token 预算。

成本记录：去重源帧数、累计图片展示、视觉/文本输入 token、输出 token、模型调用、预处理/解码/索引/查询耗时、峰值显存。API 缺失的细分用量标为 unknown，不填零。输入预算以可用 processor/服务能力预估并预留输出余量，实际消耗后更新；不能把事后统计误称硬预算。

## 5. P2：逐项验证讨论中的改进

### 5.1 观察状态契约

每条信息记录 `id`、`source`、`kind`、`status`、`evidence_frame_ids`、`created_turn` 及必要的修订关系。区分程序核验元信息、模型画面观察、待验证假设、证据缺口和已否定条目。

- 模型观察仍可能错误，不能因有来源标签就标为客观真值。
- 假设只能指导追加观察；必须有新增支持证据才可更新状态，重复引用不提升证据等级。
- 相关性、事件证据充分性、观察覆盖和边界清晰度分开表示；模型自评分标为未校准。
- 覆盖来自实际已观察的时间/位置；语义充分性由模型判断并接受抽查。未观察区域不得因为父节点评分而直接判定不存在目标。

### 5.2 结构与动作候选

| 候选 | 实现要点 | 关键反例 |
|---|---|---|
| 时间与内容边界融合 | PySceneDetect 等形成基础块，长块继续时间细分，相邻块可按冻结规则合并，上层按时长/预计观察成本分组 | 同一事件跨镜头、固定镜头内多个事件、快切过分割 |
| 局部连续补看 | 直接从原视频抽新增帧，区分进入子块与保持当前区间加密观察 | 稀疏帧池无法确认动作方向、短事件未采到 |
| 可验证假设 | 提出少量替代解释与需要补充的观察 | 只生成宽泛描述、把猜测累积为事实 |
| 关键历史与记忆 | 保存帧引用和证据状态，选择性重展示图片，保留完整历史用于审计 | 摘要遗漏细节、误删矛盾证据、重新展示成本被漏记 |

这些是对项目原型的改造假设，不宣称首创；VTS 已包含非均匀树、内容变化分割与导航思想。先复用工具并明确适配范围，不把简单均匀二叉树当作 VTS 官方复现。

### 5.3 实际分支对照

从同一已冻结可见状态，分别实际执行少量动作，例如换候选、当前区域补看、边界补看及立即结束。保存后续定位、证据变化与全部新增成本。GT 仅在离线评测端；不存在的分支结果不生成伪标签。结构、标签、假设与记忆逐项消融，不一次叠加后归因。

## 6. P3 与 P4：有依据后学习，再确认

- P3 门槛：训练/开发来源中不同动作确有状态相关收益，而且能够在未参与拟合的开发来源上预测；只有 oracle 能挑对动作不算通过。
- 通过后冻结 VLM，训练最小动作评分器，比较固定规则、提示词和学习选择。新监督来自实际执行结果，不直接搬用旧几何 teacher。
- P4 前冻结源码、模型、提示、预算点、输入规格、样本来源和失败计分。按源视频隔离，旧确认不用于挑模型。
- 正式确认使用新来源；自然长视频须有真实媒体和人工核对的事件标注。负查询须人工确认，不把未标注区间当负例。
- 报告定位质量、实际成本、来源配对不确定性和失败分层；不保证动态策略胜出，固定方法更好就交付固定方法。

## 7. 数据、算力与执行顺序

本机适合开发、预处理、Mock 和页面验证；已检查为 RTX 3050 Laptop 4GB、约 16GB 内存、CPU 版 PyTorch。历史帧、输入与适配器仍在归档，但不得成为当前运行隐式依赖。

真实模型实验需独立 GPU 环境：24GB 单卡有历史小预算运行依据；32/64 张及更长上下文先测，48GB 级单卡作为更宽裕的规划选项而非显存保证。准备固定基座、CUDA 环境与依赖锁；API 可作替代后端，但必须固定可识别版本并记录用量，不能混算本地模型结果。

先用约 32–64 个允许开发的来源诊断机制，正式确认数量依据开发差异和预期效应规划。新视频收集与人工证据核查先于长视频结论。GPU 时长和费用在小批量资源探针后估算，当前 TODO / 未测。

交付顺序：

1. 当前规划发布；明确现有工作区重组与新功能的边界。
2. 视频库、持久任务、查询/结果/下载闭环，完成 Mock 与页面验收。
3. 预算配置与成本记录、局部补帧、带标签观察状态，完成契约回归。
4. GPU 小批量探针、局部辨识、固定方法预算曲线。
5. 块结构与同状态追加动作实验，逐项消融。
6. 仅在门槛通过后训练控制器，冻结后新来源确认。

## 8. GitHub 发布与验收边界

- 目标仓库：`wubuxy/QuerySeek-VideoAgent`；规划在独立分支发布，不直接覆盖 main。
- 当前发布仅包含本文，不代表聚焦重组源码已同步或新页面已交付。
- 后续先审阅已有重组修改并单独提交，再按工作台、契约、实验器和研究结果分批提交；精确列出文件暂存，不使用 `git add .`。
- 不提交 `.env`、用户视频、data、outputs、归档或模型权重；公共演示使用可生成的合成素材。
- 功能提交带 pytest；源码发布前验证最小安装、Mock 完整流程及相关页面测试。真实实验和工程验收分开记录，尚未测量的收益写 TODO / 未测。
- GitHub 源码发布不等于公开托管服务。第一版给出本机启动方式；公网托管、账号体系和多用户隔离若需要，另立部署范围。
